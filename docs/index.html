Stepmeter for Jira

A tool for Jira and Confluence Cloud admins that shows which automation rules will cost the most under per-step billing, and how to rewrite them to cost less.

Started 8 Oct 2026 Billing change 3 Dec 2026 Current phase 0 · Validation

Read the one-page brief · See the demo report

The problem

From 3 December 2026, Atlassian Cloud measures automation usage in steps. Each trigger, condition, action, branch and loop that runs counts as one step, including a trigger that finds nothing to act on. Steps come from a monthly allowance pooled across the organisation. Extra usage is billed at $0.50 per 1,000 steps and is switched on by default, and Enterprise plans move from unlimited automation to an allowance. If an admin switches extra usage off, rules pause when the allowance runs out, and events missed during the pause are not replayed.

Cost now depends on how each rule is built, not only on how often it runs. A daily scheduled rule that loops over 500 work items and edits each one uses at least 15,000 steps a month on its own. A rule triggered on every work item update uses a step each time it fires, even when its condition then stops it.

Atlassian Administration shows usage by meter and app, with forecasts, alerts and limits, and each space's Automation page has a Usage tab that lists its highest-usage flows with runs and estimated steps. What it doesn't show is how many of those steps went to runs that did nothing, or how to change a flow so it uses fewer. In my test site, 4 of one flow's 7 steps were spent on runs that stopped at a condition, and nothing on the Usage tab says so.

What the tool will do

For each automation flow, show how much of its step cost goes to runs that do nothing, point to the part of the flow that causes it, and suggest a rewrite with the expected saving, before anything is changed. Secrets inside flows, such as webhook URLs and headers, are stripped before anything is processed, and flow data isn't kept.

How I'm approaching the build

  • Validate before building. A three-day spike with written stop criteria comes first. If the rule API doesn't expose rule structure, or admins already know which rules are expensive, I stop and move to the next idea on the shortlist.
  • Be clear about estimates. No public API reports how often each rule runs, so run frequency is estimated. I'll compare the estimate with Atlassian's own usage figures and publish the difference.
  • Treat secrets as a core requirement. The Rule Management API returns rule configuration in full, including values the UI masks (AUTO-2207). The tool strips them before processing and doesn't keep rule data.
  • Real users before launch. 5 to 10 admins run it on their own sites before any public release.
  • How I work. I use an AI assistant (Claude) for research and coding. Problem choice, product decisions and trade-offs are mine, and each is recorded with its reasoning in the decision log.

Journal

13 Oct 2026 · Day 5

A first demo report and a one-page brief

Built a first version of the report Stepmeter will give admins, using the test site's flows and run results: total steps, steps on runs that did nothing or failed, the cause in each flow's structure, and a suggested fix. On the test site, 12 of 57 steps (21%) went to runs that did nothing or failed, across three flows.

Wrote a one-page brief that sets out the findings and one idea for the Usage tab itself: a wasted-steps column with plain-language flags such as "edits before checking" and "fails every run".

9 Oct 2026 · Day 1, mid-morning

The API returns each flow's full structure

Ran the spike script against the test site. It listed all 9 flows and fetched each one's configuration through the Automation Rule Management API, using a classic API token with basic authentication on the site address. My first run failed with HTTP 401 because of a typo in the email address, which a login check added to the script now catches.

The response includes what Stepmeter needs to estimate cost per run: each flow's state (enabled or disabled), the trigger type, and every component in order, with branches and their children nested. The trigger type distinguishes a broad "any update" trigger from a narrow field-change trigger, and a scheduled search from an event, which are the patterns behind most of the waste found so far.

Flow configuration from this API can include secrets in plain text (AUTO-2207), and the test site has a flow with a planted fake one. The script masks secret-looking values before saving, and a search of the saved files found no trace of it.

It does not include how often each flow runs. Run frequency will have to come from another source, which is the main open problem for Phase 1.

The web request flow has only one component in the API response, so its extra step on the Usage tab doesn't come from hidden structure. A follow-up test is running.

9 Oct 2026 · Day 1, morning

Loops are billed per work item, and the model holds

Built four more flows overnight, each covering one cost pattern: a branch over sub-tasks, a daily scheduled search over 7 work items, a web request with a fake secret in it, and a flow that edits a work item before checking whether it should. I wrote down a step prediction for every run before Atlassian reported it.

56 of 57 steps matched across 17 runs on 7 flows. The one miss was the web request flow: 3 steps where I predicted 2, on a run where the request failed. I haven't explained that yet.

Branches and scheduled searches are billed per work item. The sub-task branch used 4 steps for 2 sub-tasks, not 3. The daily search used 8 steps per run, one for the trigger and one comment for each of the 7 matching work items. The audit log groups this work into one line per action, so the per-item cost isn't visible there.

Some waste is labelled "Success". When the broad flow stopped at its condition, the audit log said "No actions performed". The flow that edits first and checks second stopped at the same condition on the same work item, but because its edit had already run, the audit log called it "Success". It used 3 steps, didn't do its job, and overwrote the work item's description on the way.

Across the test site, 6 of the broad flow's 15 steps went to runs that did nothing.

8 Oct 2026 · Day 0, night

First real data from the test site

Built a test site with 30 work items and the first three flows: a simple one (created, then assign), a broad one (any update, then check for a vip label, then comment) and a narrow one (labels changed, then comment). Ran three tests that touched a vip item and a non-vip item.

The step model matched exactly. Counting one step per trigger, condition and action that ran, I predicted 11 steps across 5 runs. The Usage tab reported 11: 2, 2 and 7.

Atlassian already ranks flows by steps. Each space's Automation Usage tab has a "High usage flows" table with runs and estimated steps, sortable by steps. My assumption from the public documentation was wrong, which is what this phase was for. The tab also lags: it took about two hours to show the new runs.

The gap is waste and the fix, not the ranking. The broad flow ran 3 times for 7 steps. Two runs stopped at the condition and did nothing, yet used 4 of the 7 steps. The audit log shows those runs as "No actions performed", but the Usage tab only shows the total. Telling an admin how much of a flow's cost is wasted, and how to rewrite it, needs both the flow's structure and its run results together.

Decision: Stepmeter will focus on wasted steps and how to fix them, not on ranking flows (decision 11).

8 Oct 2026 · Day 0, evening

Phase 0 kit ready, building in public

Set up a public GitHub repository so the work is visible as it happens.

Wrote the Phase 0 kit: 17 test automation rules, each built to show one pattern that changes step cost (broad triggers, conditions placed last, branches over sub-tasks and search results, hourly schedules), a script that lists and reads every rule, and an interview guide for Jira admins.

Because the API returns secrets in full, the script strips URLs, headers and tokens before saving anything. I tested it offline on a sample rule with four planted secrets. All four were removed and the component counts were correct.

8 Oct 2026 · Day 0

From a broad goal to one problem

Started with a broad goal: find a real problem on Atlassian's platform and build something useful for it.

Three early ideas were ruled out by research: two were already shipped and one had no data access. I then reviewed about 20 ideas against three checks, verified the shortlist's key facts against Atlassian's documentation, and chose automation step cost.

Two findings shape the design. The Rule Management API accepts API tokens but not Forge or OAuth apps, so the first version will be a web tool rather than a Marketplace app. And because the API returns rule configuration in full, secret handling is a core requirement.
